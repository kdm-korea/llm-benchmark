# KoBLEX 원본·정답 매핑 검증 결과

- 수행일: 2026-10-23 (Asia/Seoul)
- 실행 기준: [KoBLEX 평가 구축 계획](../koblex-evaluation-plan.md)
- 결과: 원본 확보·정규화·정답 매핑·분할·평가 계약 v1 구축 완료. **222개 질문 사용 가능, 4개 보류**.
- 임베딩·검색 성능 실험·유료 생성 API·LLM judge는 실행하지 않았다.

## 1. 접근성, 원본 고정, 이용 조건

인증 토큰 없이 Hugging Face 공식 API와 고정 리비전 파일 URL에 접근해 다운로드했다. 앞선 브라우저 조회 오류는 QA 비공개 또는 미제공의 증거가 아니었다. [접근 확인 기록](access-check.json)에 API의 `private=false`, `gated=false`, `disabled=false`, 실제 스키마 선언을 보존했다.

[원본 manifest](source-manifest.json)에 다운로드 시작 시각 `2026-10-23T11:44:12.264263+00:00` (한국 시각 20:44:12), 고정 URL, 파일 크기와 SHA-256을 기록했다. 다운로드 후 모든 파일을 로컬에서 다시 검증했다. 이후 재확인 시각은 `data/raw/koblex/download-receipt.json`에 남는다.

원본은 `data/raw/koblex/`에 있다. QA Parquet는 455,400바이트, 법령 Parquet는 28,773,033바이트다. 두 저장소는 선언된 `test`/`corpus` 외 `train` 파일도 갖지만 각 원본 파일과 **바이트·해시가 동일**하다. 452 QA 또는 467,088 법령으로 합산하지 않았다.

공식 GitHub의 [LICENSE](https://github.com/daehuikim/KoBLEX/blob/1a2d225be33a70ebf91e2b6369acf27551dcfbb4/LICENSE)는 **Attribution-NonCommercial 4.0 International (CC BY-NC 4.0)**이다. HF 카드 두 개에는 별도 `license` 메타데이터·설명 본문·LICENSE 파일이 없다. GitHub 라이선스가 HF의 각 구성물에 어떻게 적용되는지 명시한 추가 설명은 확보한 문서에서 찾지 못했다. 출처·고정 리비전·변경 내역을 보존해 연구용으로 로컬 분석하며, 상업 이용 허용이나 HF 데이터의 독립적인 재배포 허가를 확인했다고 기록하지 않는다. 이번 Git 공유 대상은 코드·ID 장부·통계·기준 문서이며 전체 원문은 기존 ignore 정책을 따른다.

## 2. 실제 스키마와 품질

| 구분 | 실제 분할·행 수 | 필드 |
| --- | --- | --- |
| QA | `test`, 226 | 문자열 `id,question,answer,question_eng,answer_eng,background,background_eng`; `contexts`는 struct 목록; `n_hops` int64 |
| QA context | 총 443건 | 문자열 `content,content_eng,hierarchy,hierarchy_eng,index,index_eng` |
| 법령 | `corpus`, 233,544 | 문자열 `index,hierarchy,content` |

전체 행을 로컬 Parquet로 읽었다. QA의 필드와 context 하위 필드, 법령 필드에 null·빈 문자열·빈 context 목록은 없었다. QA ID·공백 정규화 질문·시나리오·답변은 각각 226개 고유 값이다. 세부 타입·검증 수치는 [audit-summary.json](audit-summary.json)에 있다.

- `n_hops`: 1-hop 57개, 2-hop 127개, 3-hop 42개.
- 실제 contexts 수: 1개 55문항, 2개 125문항, 3개 46문항.
- `n_hops != len(contexts)`인 질문 6개가 있다. 원본 값을 보존하고 근거 수의 분모는 contexts의 고유 evidence ID로 계산한다. ID 목록은 audit summary에 있다.
- 질문 안의 완전히 같은 주석 근거 반복은 0건이다.
- 법령 시행일·공포일·버전 ID, 질문의 구조화된 사건 기준 날짜, 필수/보조 근거 구분 필드는 없다. 본문의 개정 표시나 시나리오의 연도를 시행일 필드로 대신하지 않았다. 내부 `effective_date`, `case_date`는 null이다.

`index`나 `hierarchy`를 딕셔너리의 단일 본문 키로 사용하면 원본이 덮어써진다. 이번에는 원문 3필드와 리비전 해시로 unit ID를 만들고 모든 원본 위치를 보존했다. 같은 계층명의 다른 본문은 개정판이라고 단정하거나 한쪽을 임의 삭제하지 않았다.

| 본문 패턴에 따른 종류 | 원본 행 | 정규 단위 |
| --- | ---: | ---: |
| 편·장·절·관 제목 | 6,175 | 5,613 |
| 본문 없는 조 제목 | 37,479 | 33,637 |
| 조 본문 | 23,839 | 21,713 |
| 항 | 139,413 | 124,350 |
| 호 | 26,633 | 24,246 |

즉 모든 행이 항 단위가 아니다. 기타 5개에는 헌법 전문·날짜와 민법의 `제1항 협의상 파양` 같은 구조 제목이 있다. 패턴 분류가 법률 구조를 완전히 판정하는 것은 아니다. 기타는 자동으로 삭제하지 않고 원문을 보존했다.

구문상 고유 부모 148,586개, 복수 부모 후보 10개, 조 단위 또는 부모 미확인 root 55,355개, 별도 구조 제목 5,613개다. 부모 후보는 같은 index 안의 hierarchy 접두사로 계산한다. 장/절의 원본 위치를 보존하지만 완전한 법령 트리·개정 계보를 복원한 것으로 해석하지 않는다.

## 4. 정답 매핑과 보류

## 5. 검수 표본과 분할

[표본 점검 기록](review-samples.json)은 17개 질문(dev 3, test 10, 보류 4)을 포함한다. Codex가 로컬 고정 QA의 시나리오·질문·참고 답변·근거 본문과 매핑을 읽어 점검했다. 단일 근거, 복수 근거, 정확 중복, 조·호 결합, 순서 차이, 단서·예외, 법/시행령 구분, n_hops 불일치 및 보류 4개를 포함한다. 별도의 법률 전문가 또는 독립 검수자의 검토는 수행하지 않았다.

표본에서 조 제목이 같아도 본문과 조문 번호를 확인해야 함을 확인했다. 상업등기법26조와 형사소송법361조의5의 QA는 호 순서가 사전식으로 보이지만 전체 본문은 코퍼스와 일치했다. 선원법22조 사례는 2-hop 표기에도 실제 근거 3개이며 해원 수 10명 이하의 예외까지 보존했다. 일부 참고 답변은 시점·전제·법적 충분성에 추가 의미 검수가 필요하다. 이 결과만으로 현재법의 정답 정확도를 추정하지 않았다.

분할은 [splits.json](splits.json)에 고정했다. **dev 44, test 178, holdout 4**, 총 186그룹, 가장 큰 그룹 3개 질문이다. source ID family와 문자 5-gram Jaccard 0.65 이상의 연결을 사용하고 seed `20261023`으로 개발 20%를 배정했다. 모든 44개 유사도/ID 연결과 그룹 배정을 재현했다. 같은 그룹은 dev/test 사이에 걸치지 않는다. 완전한 의미 중복 탐지나 unseen-law 분할은 아니다. 주석 근거 10개는 두 분할에 공유되며 코퍼스는 전체 공통으로 유지한다.

## 6. 평가 기준과 검증

[검색 계약](evaluation-rules.md)은 K=1/5/10/20/50/100, Evidence Recall·Hit·주석된 All-evidence Hit·MRR@100, 중복 청크, 다중 행 근거, 문자 구간 포함 기준을 정의한다. 주 지표는 원본 context의 전체 본문을 엄격하게 요구한다. 질문 해결에 충분한 최소 구간의 정답을 새로 구축한 지표가 아니며, 필요 이상의 호가 주석된 사례에서는 이를 한계로 보고한다.

[답변 검수표](answer-rubric.md)는 결론·완전성·충실성·인용·복수 조문 적용·정보 부족 대응을 분리했다. 원본 LF-Eval은 고정 코드를 읽었으며 기본 judge/의존성 미고정, ID join 부재, 800문자 절단, README/구현 입력 차이 등이 있어 이번에 실행하지 않았다. 후속 비교용 후보로 남기고 생성 모델·프롬프트·합격선을 임의 확정하지 않았다.

검증 환경은 Python3.12.10, PyArrow26.0.0이다.

- 원본 15개 파일의 크기·SHA-256 검증, train 동등성 검증.
- 전체 법령·QA·context 스키마·결측·행 수·중복·매핑 점검.
- qrels의 모든 unit 존재 여부, 이상적인 완전 근거 입력에서 모든 지표 1, 빈 결과에서 모든 지표 0 확인. 이는 검색 성능 결과가 아닌 계산 검증이다.
- 독립 예제 테스트 8개: 중복과 부모 모호성, 엄격 매핑, 호 순서와 교차 조문 불일치, 공백 충돌, 근거 단위 누적·중복 방지, 미해결/누락 실행 오류, 구간 누락·제목 제외, 그룹 분할 재현.
- 저장소 전체 테스트 **25개 통과**.
- 재실행 전후 정규화 파일 6개와 manifest까지 **7개 파일의 바이트·SHA-256 동일** 확인. JSON 형식·문서 내부 링크·분할/표본 수·의존성 잠금 메타데이터도 확인했다.

재현 명령·산출물 위치는 검색 계약에 있다. 원본·정규화 파일은 Git 제외이며 생성한 코드·문서·ID 목록을 남겼다. 기존 다른 작업의 변경을 보존했고 커밋·브랜치를 만들지 않았다.

## 7. 완료 범위와 후속 조건

현재 사용 가능한 질문과 보류 질문을 구분한 평가 기반 v1을 구축했다. 남은 제한은 4개 근거 불일치, 구조화된 법령 시점 부재, 원본 정답의 필수/보조 구분 부재, 독립 법률 전문가 답변 검수 미실시다. 이 제한을 해소했다고 표시하지 않는다.

다음 연구에서는 이 버전을 고정해 KURE-v1 검색 기준선을 실행할 수 있다. 사용 단위·제목 포함 방식·중복 제거·검색 입력·동점 규칙을 기록하고 dev만으로 설정을 선택한 후 test를 사용한다. 의미 검수로 근거를 수정하거나 4개 보류를 편입하는 경우에는 데이터 버전·분할·해시를 갱신하고 v1 점수와 분리한다. 임베딩과 생성 실험은 이번 범위에서 실행하지 않았다.
